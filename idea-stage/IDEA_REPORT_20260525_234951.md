# SignalClaw Research Idea Report

**Direction**: 基于 Pi-Light 做可落地 SignalClaw，输出两套边缘可执行 skills：信号周期规划、下一相位规划。
**Generated**: 2026-05-25
**Ideas evaluated**: 10 generated -> 5 survived filtering -> 0 piloted -> 2 recommended
**Hard constraint**: 同一交通输入不能回放探索不同动作空间；SUMO 只能做真实落地式单时间线回放。

## Landscape Summary

Pi-Light 的贡献是把信号控制策略表示成可解释、轻量、可部署的程序 DSL，但其学习过程仍依赖 MCTS 与候选程序 episode 评估。对 SignalClaw 来说，这个训练范式不合适：真实落地系统不能对同一个观测状态尝试多个动作，也不能把 SUMO 当作可任意分叉探索的 RL 环境。

真实 SQL 数据更像“业务闭环日志”而不是 RL 数据集。`cycle_time`、`run_timing_adjustment`、`phase_green_event`、`traffic_flow_record`、`prediction_record`、`batch_plan` 和 `wave_node` 已经覆盖了周期、相位、流量、预测、执行、绿波 offset。最自然的学习对象是从这些日志中归纳可执行策略，而不是学习 Q 函数。

当前 SUMO 场景只有 1 小时，且与真实 SQL 路口/相位映射不一致。因此 SUMO 在第一阶段应定位为“顺序回放验证器”：给定真实/合成的时间线与单一策略，按时间推进并记录指标。它不能用于对同一状态分叉测试多个动作。

## Generated Ideas

### Idea 1: Counterfactual-Free Dual-Skill DSL - RECOMMENDED

- **Summary**: 从真实日志中归纳两套可解释 DSL 程序：周期规划 skill 和下一相位规划 skill，训练和评估全程不做同状态多动作探索。
- **Hypothesis**: 真实日志中的周期配时、AI 微调、实际运行时长与相位事件已经包含足够强的专家策略信号，可以归纳出比固定基础规则更稳健、比神经 RL 更可部署的程序策略。
- **Minimum experiment**: 用 `run_timing_adjustment + prediction_record + traffic_flow_record + phase_green_event` 构建监督样本；学习 DSL 程序；在留出日期/路口上评估模仿误差、约束违例、相位稳定性，再用 SUMO 单时间线回放对比基础规则。
- **Expected outcome**: 成功时，实际 duration MAE 降低、min/max green 违例为 0、相位切换更稳定；失败时，说明日志策略不可归纳或需要更细粒度 detector 特征。
- **Novelty**: 8/10。最近工作有 Pi-Light、GPLight/GPLight+、SymLight，但多依赖仿真搜索/GP/MCTS。差异点是日志约束、无反事实动作探索、两级可部署 skill。
- **Feasibility**: 高。已有 SQL 和 Pi-Light DSL 代码；需要先做 SQL 抽取与路口相位映射。
- **Risk**: MEDIUM。
- **Contribution type**: 方法 + 系统 + 实证。
- **Pilot result**: SKIPPED。当前阶段未建立 SQL 抽取和 SUMO 单时间线 harness；GPU 不需要，后续可做 CPU 级 pilot。
- **Reviewer's likely objection**: “只是模仿历史策略，怎么证明优于人工规则？”必须用时间留出、路口留出、异常时段与 SUMO 顺序回放证明稳健性。
- **Why we should do this**: 它最贴合落地约束，也最能把 Pi-Light 的边缘部署优点保留下来。

### Idea 2: Conservative Log-Constrained Pi-Light Distillation - RECOMMENDED BACKUP

- **Summary**: 保留 Pi-Light 的 lane-link priority 聚合结构，但把 MCTS 搜索替换为日志约束蒸馏：从真实相位执行和流量峰值拟合 priority 程序。
- **Hypothesis**: Pi-Light 的 `v += in_wait / v -= out_count` 类结构足够表达真实信号调控中的主要压力逻辑，参数可由日志拟合而非仿真搜索得到。
- **Minimum experiment**: 把每个相位的方向流量、红灯峰值、当前/邻接 one-hot 映射成 phase score，拟合稀疏线性/树模型，再导出 Pi-Light 风格 DSL。
- **Expected outcome**: 能生成短程序，复现大多数历史下一相位或 duration 调整；失败时说明真实系统依赖更复杂的时段/绿波/人工干预逻辑。
- **Novelty**: 7/10。与 Pi-Light 近，但训练范式不同。
- **Feasibility**: 高。直接复用 `pi_light_code/agent/pi_light/program.py` 的抽象。
- **Risk**: LOW-MEDIUM。
- **Contribution type**: 方法 + 工程落地。
- **Pilot result**: SKIPPED。需要先从 SQL 建立相位/方向训练表。
- **Reviewer's likely objection**: “创新性不如完整 dual-skill 框架。”适合作为可快速落地的备份线。
- **Why we should do this**: 它是最小改造 Pi-Light 的路径，能尽快产出边缘代码。

### Idea 3: Neighbor One-Hot Coordination Without MARL

- **Summary**: 不做多智能体通信学习，只把邻接路口相位、周期位置、绿波节点身份 one-hot 编入 DSL 条件，使局部程序自发协调。
- **Hypothesis**: 邻接 one-hot 足以表达大部分相邻路口协同需求，尤其是干线绿波和队列外溢预警。
- **Minimum experiment**: 构造 `self_state + neighbor_phase_onehot + wave_node_onehot + offset_error` 特征，比较有/无邻接 one-hot 的日志模仿误差和 SUMO 顺序回放指标。
- **Novelty**: 7/10。区别于 CoLight/GNN/MARL 的神经通信，用可解释离散上下文实现协同。
- **Feasibility**: 中。真实 `crossing.sumo_id` 当前多为 0，需要补齐路口邻接映射。
- **Risk**: MEDIUM。
- **Contribution type**: 方法 + 诊断。
- **Pilot result**: SKIPPED。
- **Reviewer's likely objection**: 邻接 one-hot 可能只是在记忆路口身份，不是真正泛化。需要路口留出实验。

### Idea 4: Green-Wave Offset Skill as a Separate Edge Program

- **Summary**: 将绿波/红波 `wave_node.offset` 拆成独立的 offset skill，周期 skill 只输出相位时长，offset skill 负责路口间相位差校正。
- **Hypothesis**: 把 offset 从 duration 决策中解耦，可以降低策略复杂度，并更接近交通工程实际部署。
- **Minimum experiment**: 对有 `wave_node` 的路口，拟合 offset 修正规则；在 SUMO 单时间线回放中比较走廊通行时间与停车次数。
- **Novelty**: 6/10。绿波优化是经典问题，但和日志约束 DSL 结合有落地价值。
- **Feasibility**: 中。当前 `wave_node` 数据较少，可能需要人工补充绿波路线。
- **Risk**: MEDIUM。
- **Contribution type**: 系统 + 实证。
- **Pilot result**: SKIPPED。
- **Reviewer's likely objection**: 数据量少，可能只能作为工程模块而非主论文贡献。

### Idea 5: Uncertainty-Gated Safe Fallback Skill

- **Summary**: 给两套 skill 增加置信度门控：当状态超出日志支持域、传感器异常或预测不稳定时，回退到基础配时/人工规则。
- **Hypothesis**: 可部署系统的关键不是始终自动控制，而是在分布外状态下保守退出。
- **Minimum experiment**: 用历史流量分布、相位异常、执行偏差定义 OOD 指标；评估门控对违例率和极端错误的降低。
- **Novelty**: 6/10。安全门控常见，但与可解释 TSC skill 和真实 SQL 闭环结合有价值。
- **Feasibility**: 高。
- **Risk**: LOW。
- **Contribution type**: 系统安全 + 诊断。
- **Pilot result**: SKIPPED。
- **Reviewer's likely objection**: 单独作为论文贡献偏弱，但作为 Idea 1 的关键模块很强。

## Eliminated Ideas

| Idea | Reason eliminated |
|---|---|
| Pi-Light MCTS on SUMO Chengdu | 需要对候选程序重复 episode 评估，违反同状态不可多动作探索约束。 |
| CoLight/MARL with neighbor communication | 常规 MTSC/MARL，需要动作探索和反事实评估，不符合落地闭环。 |
| Offline Q-learning / Conservative Q-learning for next phase | 即使是 offline RL，也隐含对未执行动作的价值估计；在当前数据和安全约束下风险过高。 |
| Full digital twin calibration as the main idea | 必须做，但更像基础设施；缺少两套 edge skill 的核心方法贡献。 |
| LLM traffic-signal planner | 不适合边缘设备、不可审计，且难以满足硬实时和安全约束。 |

## Pilot Experiment Results

当前没有运行模型 pilot。原因：

- Phase 2 仍处于 idea generation/filtering。
- SQL 数据 5GB，需先建立抽取表和训练样本。
- SUMO 场景与真实 SQL 未对齐，直接 pilot 会误导结论。
- 更重要的是，任何 pilot 都必须使用单时间线日志/回放，不能做同状态多动作试验。

建议下一步的 CPU 级 pilot：

| Pilot | Time | Success Metric | Signal |
|---|---:|---|---|
| P1 SQL training table extraction | 1-2h | 能为 crossing/cycle/phase 构建样本，缺失率可解释 | REQUIRED |
| P2 fixed-rule vs log policy reconstruction | 1-2h | actual_duration MAE、min/max green 违例率 | REQUIRED |
| P3 SUMO no-fork replay harness | 2-4h | 单时间线动作日志完整，禁止 state fork | REQUIRED |

## Suggested Execution Order

1. **Idea 1**: 作为主线，先做数据抽取、DSL 设计和单时间线评估协议。
2. **Idea 2**: 作为快速备份，先蒸馏 Pi-Light 风格短程序。
3. **Idea 3**: 在真实邻接/SUMO 映射补齐后加入，验证 one-hot 协同是否真的有贡献。
4. **Idea 5**: 作为所有上线版本必须包含的安全模块。
5. **Idea 4**: 绿波数据足够后作为增强模块。

## Recommended Next Phase

进入 novelty-check / deep validation 时，应重点验证：

1. 是否已有工作明确做“无反事实动作探索”的 TSC 程序归纳。
2. Pi-Light/GPLight+/SymLight 与本方案的训练和评估差异是否足够强。
3. 真实日志 + SUMO 单时间线回放是否能形成可发表的实验协议。

如果进入 implementation planning，第一步不是训练模型，而是定义数据契约：

- 周期级样本：`crossing_id, cycle_id, start_time, base_plan, flow_features, prediction_features, neighbor_context, target_phase_durations`
- 相位级样本：`crossing_id, cycle_id, phase_id, current_phase, elapsed, flow_features, red_peak, neighbor_onehot, legal_next_mask, target_next_or_extend`
- 回放日志：`time, state_hash, selected_action, executed_action, constraint_status, metric_snapshot`
